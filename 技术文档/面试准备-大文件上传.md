> 1. 大文件上传时间长，容易网络超时
> 2. 上传失败后需要重新上传整个文件，用户体验差
> 3. 大文件处理会阻塞主线程，导致页面卡顿
> 4. 无法支持断点续传，网络中断后前功尽弃"

### 任务目标（Task）

**标准回答：**
> "我的任务是设计并实现一个大文件上传功能，需要满足以下需求：
> 1. 支持大文件（GB级别）上传
> 2. 支持断点续传，网络中断后可继续上传

> "我采用了**分片上传 + 后端合并**的方案：
> - 将大文件切分成多个小分片（2MB/片）
> - 分片并发上传到服务器
> - 所有分片上传完成后，服务器端合并

> - 内存占用低，只处理单个分片

> - 使用 Web Worker 避免阻塞主线程

>

## 💡 常见面试问题及标准答案

### Q1: 为什么选择分片上传而不是直接上传？

**标准答案：**
> "主要有三个原因：
> 
> **1. 网络容错性**
> - 大文件上传时间长，容易网络超时
> - 分片上传后，单个分片失败只需重传该分片，其他分片不受影响
> 
> **2. 内存占用**
> - 直接上传需要将整个文件加载到内存，大文件可能导致浏览器崩溃
> - 分片上传每次只处理一个分片（2MB），内存占用固定且小
> 
> **3. 断点续传**
> - 分片上传可以记录已上传的分片，支持断点续传
> - 直接上传失败后需要重新上传整个文件"

**加分回答：**
> "另外，分片上传还支持并发上传，可以同时上传多个分片，提高上传速度。而且服务器端可以并行接收分片，处理能力更强。"

---

### Q2: 为什么使用 Web Worker？它解决了什么问题？

**标准答案：**
> "Web Worker 解决了**主线程阻塞**的问题：
> 
> **问题：**
> - 大文件切片和 Hash 计算是 CPU 密集型操作
> - 在主线程执行会导致页面卡顿，用户体验差
> 
> **解决方案：**
> - 使用 Web Worker 在后台线程处理
> - 主线程保持响应，用户可以继续操作页面
> 
> **实际效果：**
> - 5GB 文件 Hash 计算需要几分钟，但页面完全不卡顿
> - 用户可以继续浏览页面，体验流畅"

**加分回答：**
> "我还利用 Web Worker 的多线程特性，将文件切片和 Hash 计算并行处理，进一步提升性能。同时通过进度回调，实时显示处理进度，提升用户体验。"

### Q3: IndexedDB 和 localStorage 有什么区别？为什么选择 IndexedDB？

**标准答案：**
> "主要有三个区别：
> 
> **1. 存储容量**
> - localStorage: 5-10MB
> - IndexedDB: 几GB
> 
> **2. 数据类型**
> - localStorage: 只能存储字符串
> - IndexedDB: 可以存储二进制数据（Blob）
> 
> **3. 性能**
> - localStorage: 同步操作，可能阻塞
> - IndexedDB: 异步操作，不阻塞主线程
> 
> **选择原因：**
> - 大文件分片数据量大，需要大容量存储
> - 分片是 Blob 类型，需要存储二进制数据
> - 异步操作不会阻塞主线程，性能更好"

**加分回答：**
> "IndexedDB 还支持索引查询，我可以根据 fileHash 快速查找文件元数据，实现断点续传功能。而且 IndexedDB 是持久化存储，页面刷新后数据不会丢失。"

---

### Q4: 为什么选择后端合并而不是前端合并？

**标准答案：**
> "主要考虑三个因素：
> 
> **1. 内存占用**
> - 前端合并需要将所有分片保存在内存中
> - 5GB 文件需要 5GB+ 内存，可能导致浏览器崩溃
> - 后端合并只需要保存单个分片，内存占用低
> 
> **2. 断点续传**
> - 前端合并失败后需要重新合并所有分片
> - 后端合并时，服务器已保存所有分片，只需合并即可
> 
> **3. 处理能力**
> - 服务器可以使用多线程/多进程合并
> - 可以使用流式处理，不占用大量内存
> - 处理能力更强，适合大文件"

**加分回答：**
> "后端合并还有一个优势：可以验证文件完整性。服务器可以检查所有分片的 Hash，确保文件完整无误后再合并，提高数据安全性。"

### Q5: 如何实现断点续传？

**标准答案：**
> "断点续传的核心是**文件唯一标识 + 进度记录**：
> 
> **1. 文件唯一标识**
> - 使用文件 MD5 Hash 作为唯一标识
> - 相同文件生成相同 Hash，可以识别是否为同一文件
> 
> **2. 进度记录**
> - 将已上传的分片索引保存到 IndexedDB
> - 同时保存文件元数据（fileHash、totalChunks 等）
> 
> **3. 恢复流程**
> - 页面刷新后，通过 fileHash 查找已保存的元数据
> - 加载已上传的分片索引，只上传未完成的分片
> 
> **4. 服务器端校验**
> - 上传前调用接口检查服务器已上传的分片
> - 避免重复上传，提高效率"

**加分回答：**
> "我还实现了服务器端的断点续传支持。上传前会先调用检查接口，获取服务器已上传的分片列表，只上传缺失的分片。这样即使前端数据丢失，也能从服务器恢复。"

### Q6: 如何控制并发上传数量？

**标准答案：**
> "我实现了一个**请求队列**来控制并发：
> 
> **核心思路：**
> - 维护一个任务队列和运行计数器
> - 当运行数 < 最大并发数时，从队列取出任务执行
> - 任务完成后，运行数减1，继续处理下一个任务
> 
> **实现细节：**
> ```typescript
> class RequestQueue {
>   private queue: Task[] = []
>   private running: number = 0
>   private maxConcurrent: number = 3
>   
>   async add(task: Task) {
>     this.queue.push(task)
>     this.process()
>   }
>   
>   private async process() {
>     if (this.running >= this.maxConcurrent) return
>     const task = this.queue.shift()
>     this.running++
>     await task.execute()
>     this.running--
>     this.process()
>   }
> }
> ```
> 
> **优势：**
> - 控制并发数量，避免服务器压力过大
> - 支持优先级队列，重要文件优先上传
> - 自动重试机制，提高成功率"

**加分回答：**
> "我还根据网络情况动态调整并发数。网络快时增加并发数，网络慢时减少并发数，甚至串行上传，提高上传成功率。"

### Q7: WebSocket 和 HTTP 轮询有什么区别？为什么选择 WebSocket？

**标准答案：**
> "主要区别：
> 
> **1. 实时性**
> - HTTP 轮询: 需要客户端主动请求，有延迟
> - WebSocket: 服务器主动推送，实时性好
> 
> **2. 服务器压力**
> - HTTP 轮询: 需要频繁请求，服务器压力大
> - WebSocket: 长连接，服务器压力小
> 
> **3. 网络开销**
> - HTTP 轮询: 每次请求都有 HTTP 头开销
> - WebSocket: 建立连接后，只有数据开销
> 
> **选择原因：**
> - 上传进度需要实时更新，WebSocket 更合适
> - 减少服务器压力，提高性能
> - 支持双向通信，可以发送客户端消息"

**加分回答：**
> "我还实现了降级方案。如果 WebSocket 连接失败，会自动降级为 HTTP 轮询，确保功能可用。同时实现了自动重连机制，提高连接稳定性。"

### Q8: 如何计算上传进度和速度？

**标准答案：**
> "进度计算：
> 
> **1. 基于已上传分片**
> ```typescript
> let uploadedBytes = 0
> uploadedChunkIndices.forEach(index => {
>   uploadedBytes += chunks[index].blob.size
> })
> const progress = (uploadedBytes / file.size) * 100
> ```
> 
> **2. 速度计算**
> ```typescript
> const now = Date.now()
> const timeDiff = (now - lastUpdateTime) / 1000  // 秒
> const bytesDiff = uploadedBytes - lastUploadedBytes
> const speed = bytesDiff / timeDiff  // 字节/秒
> ```
> 
> **3. 进度更新**
> - 每个分片上传完成后更新进度
> - 使用节流，避免频繁更新（每100ms更新一次）
> - WebSocket 推送服务器端的进度，双重保障"

**加分回答：**
> "我还实现了进度平滑显示。使用动画效果，避免进度条跳跃，提升用户体验。同时显示预计剩余时间，让用户了解上传进度。"

### Q9: 如何处理上传失败和错误？

**标准答案：**
> "我实现了完善的错误处理机制：
> 
> **1. 自动重试**
> - 单个分片失败自动重试，最多3次
> - 使用指数退避策略，避免频繁重试
> ```typescript
> let retryCount = 0
> while (retryCount < 3) {
>   try {
>     await uploadChunk(chunk)
>     break
>   } catch (error) {
>     retryCount++
>     await sleep(Math.pow(2, retryCount) * 1000)
>   }
> }
> ```
> 
> **2. 错误分类**
> - 网络错误：自动重试
> - 服务器错误：提示用户，支持手动重试
> - 取消操作：不抛出错误，正常处理
> 
> **3. 错误提示**
> - 显示具体的错误信息
> - 提供重试按钮
> - 记录错误日志，便于排查"

**加分回答：**
> "我还实现了错误恢复机制。如果某个分片多次重试失败，会标记为失败分片，用户可以手动重试。同时记录失败原因，帮助排查问题。"

## 💬 常见追问问题

### Q: 如果文件很大（比如 10GB），你的方案还能用吗？

**答案：**
> "可以，但需要一些优化：
> 1. **分片大小调整** - 10GB 文件可以使用 5MB 分片，减少分片数量
> 2. **并发数调整** - 根据网络情况动态调整并发数
> 3. **服务器端优化** - 使用流式处理，不占用大量内存
> 4. **存储优化** - IndexedDB 有容量限制，需要及时清理
> 
> 实际上，我设计的方案已经考虑了可扩展性，通过配置可以适应不同大小的文件。"

### Q: 如果用户在上传过程中关闭浏览器怎么办？

**答案：**
> "我的方案已经支持这种情况：
> 1. **数据持久化** - 上传进度保存在 IndexedDB，浏览器关闭后数据不丢失
> 2. **文件 Hash 标识** - 使用文件 Hash 作为唯一标识
> 3. **恢复机制** - 用户重新打开页面后，可以通过文件 Hash 恢复上传进度
> 
> 不过有一个限制：File 对象无法恢复，用户需要重新选择文件。但上传进度可以恢复，只上传未完成的分片。"

### Q: 如何防止用户上传重复文件？

**答案：**
> "可以通过文件 Hash 实现：
> 1. **计算文件 Hash** - 上传前计算文件 MD5 Hash
> 2. **服务器端检查** - 调用接口检查服务器是否已有相同 Hash 的文件
> 3. **秒传功能** - 如果文件已存在，直接返回文件地址，无需上传
> 
> 这个功能我已经在代码中预留了接口，只需要服务器端支持即可实现。"
